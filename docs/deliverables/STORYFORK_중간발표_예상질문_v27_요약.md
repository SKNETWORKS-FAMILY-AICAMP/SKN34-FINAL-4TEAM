# STORYFORK 중간발표 Q&A 요약 (발표 현장용)

상세 근거: [예상질문 v27 전체본](./STORYFORK_중간발표_예상질문_v27.md)

## 답변 3원칙
1. **목표 / 시험 / 구현을 구분해서 말한다.** 슬라이드 27~29장은 목표 시안이다.
2. **수치는 지어내지 않는다.** 정확도·비용·시간은 "최종발표 전 측정"이라고 답한다.
3. **AI는 제안만 하고, 반영은 작가가 승인한다.** 막히면 이 문장으로 돌아온다.

## ★ 질문별 한 줄 답

### 기획·차별점
| 질문 | 한 줄 답 |
|---|---|
| ChatGPT와 차이 | 문장 생성이 아니라 세계관·공개 범위·버전·Fork 기준점을 관리하면서 AI를 선택적으로 쓰는 창작 환경이다. |
| 기존 웹소설·팬픽과 차이 | 원작자가 허용한 회차에서 시작하고, 기준 회차·버전을 기록하며, 원작·원작자를 표시한다. |
| 원작자가 허용할 이유 | 허용은 선택이다. 독자 참여 확대와 원작 유입을 기대한다(검증 전). 수익 배분은 미정이라 약속하지 않는다. |

### Fork·저작권
| 질문 | 한 줄 답 |
|---|---|
| Fork 저작권 구분 | 새로 쓴 부분은 Fork 작성자, 원작 부분은 원작자 권리가 남고, 원작자 허락 범위 안에서만 이용한다. 회사는 가져가지 않는다. |
| 바로 공개 가능한가 | 건건 승인이 아니라 사전 설정이다. 생성 허용과 공개 허용을 따로 두고, 공개 허용이 없으면 공개 불가다. |

### AI·에이전트
| 질문 | 한 줄 답 |
|---|---|
| 왜 여러 에이전트인가 | 한 문맥에서 여러 인물을 맡으면 정보가 섞인다. 인물별로 문맥을 나누려는 것이며, 효과는 가설이고 검증할 계획이다. |
| 에이전트 구현 | 현재는 단일 이어쓰기 제안 호출뿐이다. 다중 인물은 목표이고, 같은 모델에 인물별 문맥을 넣는 방식이다. |
| 인물 문맥 구성 | 작가가 성격·말투·목표·관계·기억·아는 정보를 등록하고, 기준 회차·공개 범위에 맞춰 선별한다. 다중 인물 구성은 목표다. |
| 모르는 정보를 말하지 않게 | 프롬프트로 지시하지 않고, 모르는 정보를 애초에 문맥에 넣지 않는다. 실제로 지켜지는 비율은 아직 측정 전이다. |

### RAG·데이터
| 질문 | 한 줄 답 |
|---|---|
| RAG는 어디에 | 벡터 RAG는 MVP 제외다. 지금은 기준 회차·공개 범위로 문맥을 선별해 조회하고, 벡터 검색은 이후다. |
| 권한 맞는 정보만 | 콘텐츠 서비스가 작품·기준 회차·범위를 고정하고 소유권을 확인한 문맥만 AI에 전달한다. 유출 방지 평가는 예정이다. |
| 홍길동전을 고른 이유 | 저작권이 끝난 고전이라 권리 문제가 적고, 방향 있는 가족 관계를 확인하기 쉽다. 일반화가 아닌 소규모 시험이다. `[판본 출처 확인]` |
| 홍길동전에서 발견한 오류 | 장소 관계 후보에서 연결 대상이 잘못됐을 가능성을 발견했다. 그래서 근거 대조와 작가 승인이 필요하다. 정확도 수치는 아직 없다. |

### 평가·비용
| 질문 | 한 줄 답 |
|---|---|
| 일관성 측정 | 아직 결과는 없고 평가 설계 단계다. 허용 문맥 사용 여부, 설정 충돌, 응답 시간·비용을 본다. |
| 일반 LLM·문맥 조회·다중 역할 비교 | 같은 장면을 세 조건으로 실행해 같은 체크리스트로 비교할 계획이다. 구현 범위에 따라 앞의 둘부터 한다. |
| 호출 횟수·토큰 비용 | 현재 제안은 요청당 1회 호출이고 사용량을 기록한다. 다중 인물은 인물·턴 수에 비례한다. 금액은 실측 후 제시한다. |

### 시스템·구현 현황
| 질문 | 한 줄 답 |
|---|---|
| 서비스를 왜 분리했나 | AI가 정본·권한·과금을 판단하지 못하게 책임을 나누기 위해서다. 지금은 코드 추출 단계이고 DB 전환·배포는 대기다. |
| 비공개 원고 보호 | 설정은 기본 비공개이고 서버가 권한을 판단하며, AI에는 허용된 최소 문맥만 보낸다. 서비스 간 인증은 후속이다. |
| 실제로 동작하는 것 | 로컬 확인: 인증·소유권, 집필실, 초안·버전·발행, Fork 기준점. 구현·검증 중: AI 제안 API, 서비스 분리. 후속: 그래프 DB, 크레딧, 운영. |
| 다중 캐릭터 화면 | **목표 UX 시안**이다. 실제 AI 실행 결과가 아니다. |
| 가장 어려웠던 점 | 저장 구조 재결정(RDB → 관계만 그래프 DB), 관계 이력 범위 축소, Fork 설정 승계 모델 구체화, AI 관계 후보 오류 대응. |

## 말하면 안 되는 표현
- "RAG를 썼다" → "허용 문맥을 조회해 전달한다, 벡터 검색은 이후"
- "Fork 저작권은 Fork 작성자 것" → 새 창작 부분만이다
- "작가에게 수익을 안겨 준다" → 그럴 가능성을 기대한다
- "나루토를 서비스에서 Fork할 수 있다" → 수요 가능성의 예시일 뿐이다
- "문맥 오염으로 품질이 떨어진다(입증)" → 가설이다
- "독자 피드백을 AI가 분류한다" → 독자가 유형을 고른다
- "배포 환경에서 검증했다" → 로컬 확인이다

## 정해 둘 것
- **AI 처리 동의 표현:** Fork 허용 범위에 포함, 모델 학습은 별도 동의 없이는 하지 않는다.
- **신고 시한:** 법정 기준은 즉시 중단·3일 이내 통보, 24시간은 내부 목표.
- **외부 근거 확보:** 나루토 영상, 웹소설·웹툰 댓글 캡처, 일본·국내 시장 수치(말하려면).
- **담당자 확인:** 모델 선정 기준, 프롬프트 시행착오, 홍길동전 사람·AI 역할 구분과 건수.
