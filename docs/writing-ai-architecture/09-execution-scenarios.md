# 집필 AI 실행 순서와 의존 관계 사례

[Python 실행 계약](02-ai-architecture.md#python-실행-계약-목표-미구현)의 84개 설계 사례다. **MVP**는 목표 지원 범위, **MVP · 순차**는 독립 입력을 각각 검증한 뒤 순차 실행, **MVP · 새 요청**은 확인·선택·승인 뒤 별도 요청, **MVP · 확인/차단**은 실행 전에 확인하거나 실행을 막는 동작을 뜻한다. **후속**은 해당 연결을 한 요청으로 지원하기 위한 검토 대상이다. MVP 표시는 구현 완료를 뜻하지 않는다.

`A → B`는 직렬 실행이다. `A ∥ B`는 독립 작업의 병렬 후보이며, MVP에서는 사용자 지정 순서와 계획 순서에 따라 한 번에 하나씩 실행한다. `(A ∥ B) → C`는 C가 두 결과를 기다리는 후속 합류 사례다. 대괄호는 사용자 확인·선택 또는 Content 승인·적용을 뜻한다. MVP에서 사용자 확인·선택·승인 뒤에 이어지는 작업은 새 요청으로 받는다. Writing과 Editing은 한 기능으로 센다.

| 사용자 요청 | 실행 | 확인할 사항 | MVP 범위 |

| “선택한 문장의 맞춤법만 검사해줘.” | Review | Mechanical만 수행한다. | MVP |

| “이 콘티로 11화 초안 후보를 써줘.” | Writing | Content가 확인한 콘티·대상으로 새 Text를 만든다. | MVP |

| “조선 후기 한양에서 동래까지 이동 시간이 어땠는지 찾아줘.” | Web Research | 외부 전송 동의와 실제 검색 출처를 확인한다. | MVP |
| “이 장소에서 두 인물이 만나는 상황을 시뮬레이션해줘.” | Simulation | 명시 요청과 인물별 입력·관찰 범위를 확인한다. | MVP |
| “내가 본 회차까지 기준으로 이 구절이 모순인지 시뮬레이션으로 확인해줘.” | Simulation | 독자 검증 결과와 제보 경계를 [UC-09 A5](../usecase-spec/UC-09.md)대로 적용한다. | MVP |

## 2. 선행 결과가 필요한 직렬 실행

| 사용자 요청 | 실행 후보 | 다음 단계가 받는 입력 | MVP 범위 |
|---|---|---|---|
| “11화 전개를 계획하고 그 계획으로 써줘.” | Development → Writing | Development가 집필용 BeatPlan 하나를 지정한다. 사용자가 대안 비교·선택을 요청하면 선택한 계획을 새 집필 요청에서 받는다. | MVP |
| “그 콘티로 쓰고, 방금 쓴 장면이 설정에 맞는지 봐줘.” | Writing → Review | 생성 Text의 불변 참조와 비교 기준. Finding 위치는 생성 후보 기준이다. | MVP |
| “이 대사를 고친 뒤 새 대사의 말투를 검수해줘.” | Editing → Review | Patch 후보와 후보 안의 위치. 원래 초안의 판본·선택 구간은 함께 유지한다. | MVP |
| “이 초안을 검수하고 문제가 있으면 고쳐줘.” | Review → 조건부 Editing | 정상 검수의 유효 Finding과 수정 가능한 초안 구간. 조건과 수정 입력을 각각 검증한다. | MVP |
| “설정에서 확정된 마법 제약을 찾아 그 안에서 다음 전개를 짜줘.” | Q&A → Development | 확인된 제약과 출처. 추론과 근거 부족도 구분한다. | 후속 |
| “4화에서 쓰인 호칭을 찾아 이 장면의 호칭과 대조해줘.” | Q&A → Review | 기준 회차의 근거와 현재 검수 대상의 별도 판본. | 후속 |
| “발행 회차의 선장 말투를 확인해서 이 대사에 참고해줘.” | Q&A → Editing | Content가 확인한 근거 발췌와 별도의 초안 선택 구간. Writing & Editing은 검색을 직접 호출하지 않는다. | 후속 |
| “동기가 약한 지점을 검수해서 다음 화에서 보완할 전개를 짜줘.” | Review → Development | 검수 Finding, 근거와 목표 회차. 의심 항목은 계획의 가정으로만 쓴다. | 후속 |
| “이름 충돌을 찾고, 확정된 충돌을 해결할 설정 변경안을 보여줘.” | Review → World & Plot | 확정 Finding과 검수 대상·근거. 영향 분석과 변경 후보를 돌려준다. | 후속 |
| “당시 이동 수단을 조사해서 이 장면의 고증을 검수해줘.” | Web Research → Review | 허용된 장면과 연결된 외부 근거, URL·검색 시각·상충 여부. | 후속 |
| “당시 통행 제도를 조사하고 그 제약을 활용한 사건을 짜줘.” | Web Research → Development | 외부 사실과 불확실성. 작품 설정에 추가하는 절차는 별도다. | 후속 |
| “항구를 폐쇄하면 생길 영향을 보고, 폐쇄를 가정해 다음 화를 기획해줘.” | World & Plot → Development | 영향 보고서와 사용자가 요청한 가정. 후보 변경을 확정 설정으로 사용하지 않는다. | 후속 |
| “11화를 기획하고 쓰고, 방금 쓴 내용을 검수해줘.” | Development → Writing → Review | BeatPlan을 사용한 Text와 해당 후보 참조를 차례로 전달한다. | MVP |
| “이동 시간을 조사해 장면과 비교하고, 오류가 확인되면 고쳐줘.” | Web Research → Review → 조건부 Editing | 웹 근거를 Review가 대상 구절·판본과 연결한다. 조건부 수정은 Review 결과를 기준으로 한다. | 후속 |
| “이전 회차의 호칭을 찾아 검수하고 확정된 오류만 고쳐줘.” | Q&A → Review → 조건부 Editing | 발행 판본의 비교 근거와 작성 중인 초안의 수정 범위를 각각 확인한다. | 후속 |
| “이 장면의 설정 충돌을 찾아, 이를 피해 전개를 짜고 그 안으로 써줘.” | Review → Development → Writing | Finding은 계획 제약으로, BeatPlan은 생성 원고 입력으로 쓴다. 원래 초안과 새 원고의 대상은 각각 확인한다. | 후속 |
| “통행 규칙을 바꿀 때 영향을 보고, 새 규칙을 가정해 계획하고 써줘.” | World & Plot → Development → Writing | 사용자에게 가정으로 표시한 변경 후보만 전달한다. 현행 설정을 바꾸려면 별도 승인·적용이 필요하다. | 후속 |
| “시대 자료를 조사하고 그 제약으로 장면을 기획한 뒤 써줘.” | Web Research → Development → Writing | 출처가 있는 외부 사실을 BeatPlan의 참고 자료로 사용한다. 집필 입력은 Content가 확인한다. | 후속 |

MVP의 같은 요청 안 결과 전달은 [등록된 집필 연결](02-ai-architecture.md#작업-간-입력출력)로 제한한다. 후속 연결은 전달할 자료 유형, 판본·대상과 오류 처리를 정한 뒤 검토한다. Web Research의 외부 검색에는 동의한 질문과 작가가 선택한 500자 이하 맥락만 전송한다. 다른 Agent의 결과를 자동으로 외부 검색에 포함하지 않는다.

## 3. 시뮬레이션과 사용자 선택

| 사용자 요청 | 실행 후보 | 확인·선택 지점 | MVP 범위 |
|---|---|---|---|
| “두 인물의 만남을 시뮬레이션하고 나온 장면을 검수해줘.” | Simulation → 새 Review 요청 | 저장된 가상 후보를 검수 대상으로 지정한다. 같은 Simulation을 다시 실행하지 않는다. | MVP · 새 요청 |
| “현재 설정을 확인한 뒤, 그 조건으로 두 사람의 만남을 시뮬레이션해줘.” | Q&A → Simulation | 확인된 설정 중 기준 시점에 각 인물이 알 수 있는 정보만 투영한다. | 후속 |
| “이 초안의 모순을 검수하고, 내가 지정한 장면에서 그 반응을 시뮬레이션해줘.” | Review → Simulation | Finding을 검증할 가정으로 쓸 수 있다. 인물에게 주는 자료는 별도로 검증한다. | 후속 |
| “다음 화의 사건을 먼저 짜고 그 상황을 시뮬레이션해줘.” | Development → Simulation | 예정된 상황을 가상 입력으로 쓴다. 복수 계획의 사용 기준을 확인한다. | 후속 |
| “두 사람의 첫 대화를 시뮬레이션해서 다음 화 계획의 대안을 만들어줘.” | Simulation → Development | 사용자에게 허용된 가상 기록을 기획 참고로 쓴다. 확정 사건으로 반영하지 않는다. | 후속 |
| “통행 규칙 변경의 영향을 보고, 변경을 가정해 검문 장면을 시뮬레이션해줘.” | World & Plot → Simulation | 변경 후보를 명시적인 가정으로만 사용한다. 정본 반영과 분리한다. | 후속 |
| “이동 시간을 조사한 뒤 그 시간 제약을 넣어 인물 반응을 시뮬레이션해줘.” | Web Research → Simulation | 확인된 외부 근거를 가상 상황의 제약으로 넣는다. 웹 조사 Agent는 Simulation을 직접 호출하지 않는다. | 후속 |
| “시뮬레이션하고, 내가 고른 전개를 원고로 써줘.” | Simulation → [후보 선택] → 새 Writing 요청 | 선택·수정한 후보 참조와 집필 대상·권한·판본을 새 요청에서 확인한다. | MVP · 새 요청 |
| “시뮬레이션 결과의 설정 충돌을 검수하고, 내가 고른 버전을 써줘.” | Simulation → 새 Review 요청 → [후보 선택] → 새 Writing 요청 | 검수 지적을 확인한 뒤 사용자가 선택·수정한 후보만 새 집필 요청에 전달한다. | MVP · 새 요청 |
| “계획을 짜고 그 사건을 시뮬레이션한 뒤 내가 고른 전개로 써줘.” | Development → Simulation → [후보 선택] → Writing | 계획을 가상 입력으로 쓰며 Writing에는 선택한 결과만 전달한다. | 후속 |
| “이미 고른 시뮬레이션 결과로 장면을 써줘.” | Writing | 선택된 기존 기록 참조와 접근 권한을 확인한다. | MVP |
| “인물의 기억이 부족해도 어떤 정보가 없는지 보고 진행 여부를 정할게.” | [부족 정보 안내] → 확인한 새 Simulation 요청 | 진행 여부와 필요한 입력을 새 요청에서 확인한다. 미확인 지식은 제외한다. | MVP · 새 요청 |

인물 턴은 앞선 행동이 다음 인물의 관찰을 바꾸므로 직렬이며, 장면 요약은 턴이 끝난 뒤 진행한다. 대안 후보의 동시 생성은 후속이다. 자유 입력에서 Simulation이 분류되면 별도 실행 확인을 받는다. 후보 선택과 부족 정보 확인은 [확정 정책](06-design-decisions.md#시뮬레이션)에 따라 새 요청으로 받는다.

## 4. 서로 독립인 병렬 후보

각 작업의 입력·판본·권한·동의가 독립적으로 확보되면 MVP에서는 순차로 지원한다. 실패 뒤에는 독립 작업도 새로 시작하지 않는다. 실제 동시 호출은 후속 검토 대상이다.

| 사용자 요청 | 실행 후보 | 독립인 이유 | MVP 범위 |
|---|---|---|---|
| “4화 설정을 알려주고, 별도로 지금 선택한 문장의 오탈자를 봐줘.” | Q&A ∥ Review | 발행 회차 질문과 초안 Mechanical 검수의 입력이 다르다. | MVP · 순차 |
| “항구의 작품 내 설정과 당시 실제 항구의 관행을 각각 알려줘.” | Q&A ∥ Web Research | 작품 내부와 외부 질문이 각각 완성돼 있다. 결과의 출처를 구분한다. | MVP · 순차 |
| “10화의 사건을 요약해 주고, 그 요약은 쓰지 말고 내가 준 콘티로 11화 전개를 짜줘.” | Q&A ∥ Development | 기획은 미리 제공된 콘티를 사용한다. | MVP · 순차 |
| “4화 설정을 확인하고, 별도로 이 콘티대로 11화 초안을 써줘.” | Q&A ∥ Writing | 집필 요청이 답변 내용을 입력으로 요구하지 않는다. | MVP · 순차 |
| “이 문단의 오탈자를 찾아주고, 별개로 다른 회차의 다음 장면을 써줘.” | Review ∥ Writing | 두 단계가 서로 다른 대상과 입력을 사용한다. | MVP · 순차 |
| “원고의 오탈자를 확인하고 당시 기차 요금도 조사해줘.” | Review ∥ Web Research | 기계 검수는 고증 결과를 소비하지 않는다. | MVP · 순차 |
| “현재 초안은 검수하고, 별도로 기존 콘티에서 다음 화 계획을 만들어줘.” | Review ∥ Development | 계획이 초안 검수 결과를 소비하지 않는다. | MVP · 순차 |
| “내 콘티대로 초안을 쓰고, 다른 장면을 위한 항구 자료도 찾아줘.” | Writing ∥ Web Research | 쓰는 장면과 조사 대상이 다르다. | MVP · 순차 |
| “다음 화 계획을 짜고, 별도로 기존 항구 설정을 바꿀 때의 영향을 확인해줘.” | Development ∥ World & Plot | 현행 기준 계획과 변경 영향 보고서를 각각 요청했다. | MVP · 순차 |
| “이미 준 콘티대로 한 장면을 쓰고, 별도로 다른 인물의 만남을 시뮬레이션해줘.” | Writing ∥ Simulation | Writing이 가상 결과를 집필 재료로 받지 않는다. Simulation 명시 요청은 별도로 확인한다. | MVP · 순차 |
| “이 초안의 오탈자를 검사하고, 별도로 지정한 상황을 시뮬레이션해줘.” | Review ∥ Simulation | Mechanical에 Simulation이 필요하지 않다. 사용자가 두 기능을 각각 요청했다. | MVP · 순차 |
| “이미 정해 둔 상황을 시뮬레이션하고, 별도로 다른 시대 자료를 조사해줘.” | Simulation ∥ Web Research | 가상 상황과 외부 질문이 서로의 결과를 요구하지 않는다. | MVP · 순차 |
| “이 장면의 오탈자와 설정 일관성을 각각 봐줘.” | Review 내부 Mechanical → Semantic | 같은 고정 판본에서 검사를 순서대로 실행한다. Router는 Review 한 단계로 센다. | MVP |

## 5. 병렬 분기와 합류

| 사용자 요청 | 실행 후보 | 합류 조건 | MVP 범위 |
|---|---|---|---|
| “작품 속 항구 설정과 실제 항구 관행을 찾아 이 장면과 대조해줘.” | (Q&A ∥ Web Research) → Review | 작품과 외부 근거를 모두 확인해 각 출처의 지적을 구분한다. | 후속 |
| “작품 설정과 시대 자료를 각각 확인해서 둘에 맞는 전개를 짜줘.” | (Q&A ∥ Web Research) → Development | 두 종류의 근거를 계획 제약으로 전달한다. | 후속 |
| “기존 설정과 시대 자료를 찾아보고 두 근거를 반영해 이 장면을 써줘.” | (Q&A ∥ Web Research) → Writing | 확인된 근거만 Content가 집필 입력에 넣는다. | 후속 |
| “초안의 충돌과 설정 변경 영향을 각각 분석하고, 둘을 고려한 다음 화 계획을 줘.” | (Review ∥ World & Plot) → Development | Finding과 ImpactReport의 대상·판본을 각각 확인한다. 변경 후보는 가정으로 표시한다. | 후속 |
| “가상의 만남을 시뮬레이션하고 시대 자료도 따로 조사해서, 둘을 대조해 개연성을 봐줘.” | (Simulation ∥ Web Research) → Review | 가상 기록과 외부 근거를 구분한다. 조사가 가상 기록을 검색어로 보내지 않는다. | 후속 |
| “콘티로 새 장면을 쓰고, 작성과 별도로 당시 복식을 조사해 완성된 후보를 고증해줘.” | (Writing ∥ Web Research) → Review | 고정 Text 후보와 그 장면에 연결한 외부 근거가 필요하다. | 후속 |
| “이 콘티를 쓰고 검수하되, 다른 회차의 설정 질문도 답해줘.” | Writing → Review → 별도 입력의 Q&A | Review는 Writing 결과를 사용한다. Q&A는 자체 입력을 사용한다. 실패 이후에는 새 단계를 시작하지 않는다. | MVP · 순차 |
| “이 원고를 검수하고 문제가 있으면 고쳐줘. 별도로 시대 자료도 찾아줘.” | Review → 조건부 Editing → 별도 입력의 Web Research | Editing은 Review 결과만 사용한다. 조건이 거짓이면 조사는 계속할 수 있고, 검수가 실패하면 시작하지 않는다. | MVP · 순차 |
| “현재 설정과 현실 고증을 모아 전개를 짜고, 그 안으로 쓰고 검수해줘.” | (Q&A ∥ Web Research) → Development → Writing → Review | 분기 합류와 세 단계 초과를 함께 다룬다. | 후속 |

MVP의 후속 단계는 요청한 필수 입력을 모두 검증한다. 두 선행 결과를 모으는 신규 연결과 병렬 합류는 후속 검토 대상이다. 마지막 Q&A·웹 조사처럼 이미 등록된 집필 연결과 별개인 작업은 각 입력을 확인해 순차 실행할 수 있다. [복합 실행 정책](06-design-decisions.md#복합-실행)

## 6. 반복·추가 단계·정본 적용이 있는 요청

| 사용자 요청 | 실행 후보 | 추가 계약 | MVP 범위 |
|---|---|---|---|
| “먼저 초안을 쓰고 검수해서 문제 있는 곳은 다시 고쳐줘.” | Writing → Review → 조건부 Editing | 같은 Agent 반복과 후보 판본 연결이 필요하다. 후보 기준 Finding으로 새 후보를 만들고 원래 초안 판본을 보존한다. | 후속 |
| “검수하고 고친 다음 다시 검수해줘.” | Review → Editing → Review | 처음 검수한 초안과 두 번째 검수의 수정 후보를 구분한다. | 후속 |
| “4화와 6화에서 선장이 같은 말을 했는지 각 판본 근거를 보여줘.” | Q&A 한 단계 또는 별도 Q&A 요청 | 한 질문으로 두 회차를 비교할 수 있으면 허용 판본을 대조한다. Q&A를 두 번 호출해야 하면 별도 요청으로 받는다. | MVP |
| “전개를 짜서 쓰고, 검수에 걸린 부분만 고쳐줘.” | Development → Writing → Review → 조건부 Editing | 세 단계 초과와 Writing 반복, 불변 후보 계약이 필요하다. | 후속 |
| “시뮬레이션하고 내가 고른 장면을 쓴 뒤 검수해서 필요하면 수정해줘.” | Simulation → [후보 선택] → Writing → Review → 조건부 Editing | 사용자 선택 대기, 세 단계 초과, 후보 기준 수정이 모두 필요하다. | 후속 |
| “같은 설정으로 두 장면의 전개를 각각 짜서 비교해줘.” | Development 한 단계 또는 별도 기획 요청 | 한 번의 기획에서 두 대안을 반환할 수 있다. 서로 다른 기획 호출이 필요하면 별도 요청으로 받는다. | MVP |
| “같은 초안으로 문체가 다른 수정안을 각각 만들어 비교해줘.” | 별도 Editing 요청 | 같은 기준 초안으로 문체별 후보를 별도 생성한다. 같은 계획에서 Editing을 반복하는 흐름은 후속이다. | MVP · 새 요청 |
| “설정 변경 후보를 만들고, 내가 승인해 반영하면 새 설정으로 써줘.” | World & Plot → [Content 승인·적용] → 새 Writing 요청 | 한 번의 승인은 단일 문서 또는 관계에 적용한다. 새 집필 요청에서 적용 영수증과 새 판본을 확인한다. | MVP · 새 요청 |
| “이 문장을 수정하고, 내가 승인해 적용하면 반영된 원고를 검수해줘.” | Editing → [Content 승인·적용] → 새 Review 요청 | 적용 영수증이 가리키는 새 초안 판본을 검수한다. | MVP · 새 요청 |

반복 호출과 네 단계 이상은 후속이다. 여러 결과를 단일 기능의 한 작업에서 반환할 수 있으면 그 기능의 계약을 따르고, 여러 호출이 필요하면 별도 요청으로 받는다. 승인 뒤 후속 작업은 새 요청에서 적용 영수증과 판본을 확인한다. 한 번의 승인은 단일 문서 또는 단일 관계에 적용한다.

## 7. 확인 질문·미지원·건너뜀 사례

| 사용자 요청 또는 실행 중 상태 | Python이 확인하거나 표시할 사항 | MVP 범위 |
|---|---|---|
| “인물 반응도 봐줘.” | Semantic 검수인지 실제 Simulation 실행인지 확인한다. 자유 입력에서 Simulation을 실행하려면 별도 실행 확인도 받는다. | MVP · 확인/차단 |
| “먼저 고증 자료를 찾고, 그다음 별도의 오탈자 검수를 해줘.” | 두 입력이 독립이어도 사용자가 정한 순서를 유지한다. Web Research 결과는 Mechanical에 넘기지 않는다. | MVP · 순차 |
| “기획과 검수를 해줘.” | 검수 대상을 확인한다. 기존 초안의 검수와 기획이 독립이면 순차로 실행할 수 있다. 새 계획을 검수하는 연결은 후속이다. | MVP · 확인/차단 |
| “시뮬레이션에서 제일 좋은 결과를 알아서 골라 원고로 만들어줘.” | 사용자가 후보를 선택·수정하면 그 참조를 담은 새 Writing 요청으로 받는다. | MVP · 새 요청 |
| “웹 조사에서 틀린 게 나오면 바로 고쳐줘.” | 웹 조사 직후 조건부 수정은 미지원이다. 웹 조사 → Review → 조건부 Editing은 연결 계약의 후속 검토 대상이다. | MVP · 확인/차단 |
| “어긋난 설정이 있으면 수정안을 내고 저장·발행까지 해줘.” | 수정 후보 생성과 정본 적용·발행에 필요한 별도 승인 경로를 안내한다. 작업 요청만으로 적용하지 않는다. | MVP · 확인/차단 |
| 정상 검수에 수정할 Finding이 없음 | 조건부 Editing을 건너뛰고 이유를 표시한다. | MVP · 확인/차단 |
| 검수 실패·부분 완료 또는 비교 근거 부족 | 조건부 Editing을 실행하지 않고 해당 상태를 표시한다. “오류 없음”으로 바꾸지 않는다. | MVP · 확인/차단 |
| 검수에서 의심만 발견했거나 확정 오류와 의심이 섞임 | 의심만 있으면 조건부 수정 미지원으로 안내한다. 혼합된 경우 지정된 한 구간의 확정 오류만 수정에 전달한다. 여러 구간 중 지정이 없으면 선택 후 새 요청을 안내한다. | MVP · 확인/차단 |
| 5화의 원고를 쓰라고 했지만 앞 단계가 6화의 다른 Fork 자료를 반환함 | 허용 범위·대상·판본 불일치로 그 결과를 연결하지 않는다. | MVP · 확인/차단 |
| 장면 요약 호출에서 시간 초과가 발생함 | 생성된 기록을 미완료로 보관·표시하고, 정상 완료된 Simulation 결과가 필요한 후속 작업을 시작하지 않는다. | MVP · 확인/차단 |
| 확인 대기 중 권한 또는 기준 판본이 바뀜 | 확인 내용은 새 요청으로 받으며 현재 권한과 판본을 다시 확인한다. 불일치한 입력은 사용하지 않는다. | MVP · 새 요청 |
| 승인 요청을 재전송했거나 생성 접수 응답을 잃어버림 | 동일 승인 재전송은 한 번만 적용한다. 생성 요청은 같은 키·같은 입력으로 기존 실행을 조회하며, 명시적 재생성은 새 키를 쓴다. | MVP |
