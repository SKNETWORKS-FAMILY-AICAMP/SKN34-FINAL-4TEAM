# 회차 원고 전처리 계약 (DEC-50)

[결정 목록](decisions.md#결정-목록) DEC-50 · [서비스 경계](service-boundaries.md) · [Content MCP 창구](content-mcp-contract.md)

현재 구현은 작품 작업 하나를 Celery 태스크 하나로 실행하고, 회차 결과와 적재는 Content 내부 콜백으로 기록한다. [#673](https://github.com/SKNETWORKS-FAMILY-AICAMP/SKN34-FINAL-4TEAM/issues/673)부터 Compose의 전처리 워커는 기본 3개 작업을 동시에 실행하고, 각 작업은 미저장 회차를 최대 4개씩 동시에 추출한다. 저장·정체 통합·적재 순서와 복구 조건은 [최초 구축 저장 계약](initial-build-storage-contract.md#업로드-자동-시작과-celery-큐-2026-11-20-사용자-결정)을 따른다. 아래의 회차 단위 Celery 태스크와 MCP 적재는 초기 설계의 실행 방식이다.

> 2026-11-17 사용자 정정: #344·#351·#428과 Celery/LangGraph는 참고 구현이며 필수 의존성이 아니다. 최신 develop의 저장 경계를 우선한다. 최초 구축의 영속 기록은 [초기 구축 저장 계약](initial-build-storage-contract.md)에 따라 보완 중이며 자동 실행 완료를 의미하지 않는다.

회차 추출과 정체 통합은 OpenAI Responses API의 엄격한 JSON 스키마 응답을 스트리밍으로 받는다. 완료 이벤트를 받고 스키마 검증을 통과한 결과만 Content에 전달한다. 완료 없이 끝난 응답은 출력 미완료로, 읽기 시간 초과와 전송 오류는 기존 모델 시간 초과와 응답 미확인으로 각각 처리한다.

## 목적

작가가 등록한 회차 원고(최소 100화~2,000화 규모)에서 사건·인물·설정을 뽑아 세계관과 회차별 상태로 정리한다.
회차당 LLM 호출이 여러 번이고 전체가 몇 시간 걸리므로 요청 안에서 끝내지 않고 백그라운드 작업으로 실행한다.

## 결정 (2026-11-13 사용자 확정)

| 항목 | 결정 |
|---|---|
| 작업 실행 | AI 서비스에 작업 프레임워크 **Celery**를 추가한다. 브로커는 기존 RabbitMQ를 쓴다. 회차별 추출은 서로 독립인 작업으로 나눠 병렬 실행하고, 정리 단계는 추출이 끝난 뒤 작품당 한 번 순서대로 실행한다 |
| 결과 적재 | 전처리 결과는 **Content MCP 창구로 적재**한다. AI 서비스가 정본 DB에 직접 쓰지 않는다 |
| 승인 시점 | 작가가 전처리 실행을 **시작할 때 한 번 승인**한다. 이 승인으로 전처리부터 적재까지 자동으로 진행한다 |
| 검토 방식 | 후보를 하나씩 승인한 뒤 반영하지 않는다. 작가는 **적재된 결과를 기존 화면에서 보고 수정**한다 |
| 선택하지 않은 안 | Airflow(사용자 요청으로 시작하는 작업이고 순환·사람 대기가 있어 맞지 않음), Content 안 폴러만으로 실행(병렬·재시도·동시 실행 제한을 직접 구현해야 함) |

## 처리 흐름

1. **회차별 추출 (병렬):** 회차마다 LLM 1회로 사건, 묘사(외모·성격·세계관 규칙처럼 사건이 아닌 서술), 거기 등장한 호칭(인물·장소·물건·조직·규칙)을 원문 근거와 함께 뽑는다. 근거를 확인하지 못한 항목은 그 항목만 제외한다(아래 정책 2). 호칭은 그 회차 안에서만 통하는 임시 ID를 받고, 다른 회차의 같은 이름과 연결하지 않는다.
2. **정체 정리:** 호칭을 같은 대상끼리 묶어 정식 ID를 준다. 같은 종류·같은 이름(이름에 -이·-아·-야나 조사가 붙은 호칭 변형 포함)은 기본으로 같은 대상으로 묶고, 모델이 가른 동명이인은 분리한다(정책 1). 같은 인물로 보이는 서로 다른 이름(별칭·가면·나중에 밝혀지는 정체)은 한 카드로 병합하지 않고 카드를 따로 둔 채 「동일 인물」 후보로 낸다(DEC-53): 다른 이름 카드 → 본체 카드와 "몇 화부터 같은 인물로 보이는지"를 함께 기록해 앞 회차 상태에 미래 정보가 섞이지 않게 한다. 후보는 관계가 아니며 작가가 승인해야 `identity` 관계가 된다.
3. **사건 등록:** 사건의 호칭을 정식 ID로 바꿔 회차 순서대로 정리한다.
4. **인물별 정리:** 인물이 나온 사건과 묘사를 모아 프로필·상태·기억을 구성한다.
5. **설정·아이템 정리:** 장소·물건·조직을 4와 같은 방식으로 정리한다.
6. **적재:** 정리 결과를 Content MCP 도구로 세계관과 회차별 상태에 적재한다.

3~6단계는 1·2단계 결과만 읽는다. 작가가 정체 묶음을 고치면 원문을 다시 읽히지 않고 3단계부터 다시 실행할 수 있다.
전체 스토리를 먼저 훑는 참고 단계를 두더라도 그 결과(미래 회차 정보 포함)는 추출 참고용으로만 쓰고 회차별 상태에 넣지 않는다.

## 책임

- **Content:** 실행 승인 접수, 작품·회차 소유권 확인, MCP 도구를 통한 적재 시 검증·저장, 작가 수정.
- **AI 서비스:** Celery 작업 실행, 추출·정리, 진행 상태, 완료 후 MCP 적재 호출.
- **Core:** 기존대로 인증. 크레딧 비용 안내·동의(UC-03 A3)는 기존 크레딧 계약을 따른다.

## 실행 계약 (2026-11-13, [#343](https://github.com/SKNETWORKS-FAMILY-AICAMP/SKN34-FINAL-4TEAM/issues/343))

화면 진입점은 작품 관리의 **[세계관 만들기]** 버튼이다. 이번 범위는 최초 구축만이다. 발행한 새 회차의 반영은 [발행 회차로 세계관 업데이트](initial-build-storage-contract.md#발행-회차로-세계관-업데이트-2026-11-22-사용자-결정)를 따른다.

| 항목 | 결정 |
|---|---|
| 접수 | 화면 → Content `POST /api/v1/works/{id}/world-preprocessing`(소유자만, 저장 회차 0개 422, 진행 중·완료 작업 409. 저장 버전이 없는 끝의 다음 회차 초안은 대상에서 빼고, 중간의 미저장 회차·Fork 상속 회차는 422와 사유 문구, 이미 설정이 있는 세계관은 409로 거절하며 거절하면 접수 행을 남기지 않는다) → AI `POST /internal/v1/preprocessing/jobs`(`X-Internal-Token`, 본문 `{jobId, workId, episodes:[회차 번호]}`, 202). Kotlin은 Celery 메시지를 직접 만들지 않는다. 같은 `jobId` 재접수는 실패 회차만 다시 실행한다 |
| 작업 기록·진행 상태 | Content 작업 테이블(작업 ID·작품·세계관·회원·상태 `queued/running/loading/completed/failed`·완료 수/전체 수·실패 회차·시각). 화면은 `GET /api/v1/works/{id}/world-preprocessing`만 조회한다. Celery 결과 저장소와 AI DB는 쓰지 않는다 |
| 백그라운드 인증 | 전처리 MCP 도구는 사용자 Bearer 대신 `X-Internal-Token` + 도구 인자 `jobId`로 호출한다. Content는 그 작업이 진행 중(`queued/running/loading`)일 때만 받아들이고 작업에 기록된 회원 권한으로 기존 Service를 호출한다. 종료된 작업 ID는 거절한다 |
| 읽을 원문 | 최초 접수 때 고정한 회차별 저장 버전과 해시 |
| 적재 위치 | 작품에 연결된 세계관의 **초안**. 연결 세계관이 없으면 접수 때 새 세계관을 만들어 1:1 연결한다(`work.world_studio_id`). 확정 버전은 작가가 수정 후 직접 남긴다 |
| 실패·재실행 | 모델 호출 실패 등으로 추출에 실패한 회차가 하나라도 있으면 정리 단계 전에 `failed`로 멈추고 실패 회차를 기록한다. 항목 하나의 검증 위반은 실패가 아니라 제외다(정책 2). 추출 중 원고·세계관·연결이 바뀌면 사유 코드와 함께 `failed`로 끝난다(정책 5). 적재는 `jobId`로 멱등(같은 작업의 재호출이 카드를 중복 생성하지 않음) |

### 전처리 MCP 도구 (Content, `jobId` 인증)

| 도구 | 인자 | 결과 |
|---|---|---|
| `preprocessing_episode_read` | `jobId`, `number` | `{number, title, body}` 그 회차 최신 저장 버전 |
| `preprocessing_progress` | `jobId`, `stage`(`extracting/resolving/organizing/loading`), `done`, `total`, `failedEpisodes[]`, `failed`(선택, 고정 사유 문구) | 갱신된 작업 상태 |
| `preprocessing_load` | `jobId`, `cards[]`, `relations[]`, `identityCandidates[]` | 적재 결과(카드 수·관계 수), 작업 `completed` |

`cards[]` 항목: `key`(작업 안 정식 ID), `cardType`(`character/location/organization/object/rule/event`), `title`, `aliases[]`, `body`(마크다운, 인물은 `IDENTITY.md`이며 정체 진술이 없으면 빈 문자열이다. 정책 6), `firstEpisode`(첫 등장 회차, 제안값이며 공개 설정이 아니다), 인물만 `characterDocs{soul, goal, episodes{"NN": 글}}`(`soul`은 뒤 회차의 soul 진술까지 쌓는다. 정책 6. `memory` 키는 쓰지 않음, 이야기 시작 전 기억은 인물의 첫 등장 회차에서만 `episodes{"00"}`이고 뒤 회차에서 밝혀진 것은 그 회차 기억이다)(DEC-47, 문서마다 3,000자 이하). 사건 카드 본문은 회차 번호와 참여 인물을 적는다. 표지·제목 표기는 아래 정책의 표기 계약을 따른다. 카드는 공개 설정 없이 적재한다: 작가 전용으로 시작하고 `revealFromEpisode`·`visibility`를 쓰지 않는다(DEC-53). `firstEpisode`는 작가가 'N화부터 공개'를 정할 때 보는 제안값으로 카드의 `semanticMetadata.preprocessing`에 두며 독자에게 나가지 않는다.
`relations[]` 항목: `fromKey`, `toKey`, `label`(관계명), `fromEpisode`, `ended`(선택). 관계 설명(body)은 Content가 근거 인용으로 채운다. Content가 DEC-51 회차별 관계로 변환해 `fromEpisode` 시점마다 기록한다. 카드 공개는 작가 전용(DEC-53)으로 시작하고 `relations[]`에는 `identity`를 싣지 않는다. 「동일 인물」 후보는 `identityCandidates[]` 항목(`fromKey`: 다른 이름 카드, `toKey`: 본체 카드, `episode`: 같은 인물로 보이는 회차, 근거)으로 따로 싣고 Content가 카드의 `semanticMetadata.preprocessing`에 후보로 남긴다. 후보를 관계로 올리는 것은 작가 승인이다.

원고 정체 추출의 `left`는 본체, `right`는 다른 이름 카드다. 명시적인 근거가 있는 서로 다른 인물 이름은 별도 카드로 유지한다. 다른 이름 카드의 `semanticMetadata.preprocessing.identityCandidates[]`에 두 카드 UUID, 발견 회차, 원문 인용을 보존한다. 승인 전에는 Neo4j 관계를 생성하지 않는다.

## 추출·정체 정리 정책 (2026-11-20 사용자 확정)

원고 추출은 실제 문체의 원고를 끝까지 처리하는 것을 우선한다. AI의 `organize`와 Content의 검증기(`ManuscriptExtractionVerifier`·`ManuscriptStructureVerifier`)는 같은 규칙을 따로 구현하므로 표기·basis·허용 목록을 바꾸면 같은 커밋에서 양쪽을 바꾼다.

| 결정 | 내용 |
|---|---|
| 1. 같은 이름의 재등장 | 같은 종류·같은 이름은 프로그램이 기본으로 같은 대상으로 묶는다(정체 basis `same_name`, 근거는 뒤 회차 대상의 검증된 인용). 모델이 `distinct`로 가른 쌍, 같은 이름 후보가 둘 이상인 경우, 같은 회차에 같은 이름이 둘인 경우는 묶지 않는다. 같은 이름이 앞 회차에 하나도 없을 때만 호칭 변형(`치삼`·`치삼이`·`치삼아`·`치삼은`)을 같은 이름으로 보고 같은 규칙으로 묶는다(#839): 한글 이름 끝에 받침 규칙에 맞는 접미사(`-이`·`-아`는 받침 뒤, `-야`는 받침 없는 뒤)나 조사(`은`·`을`은 받침 뒤, `는`·`를`·`가`는 받침 없는 뒤, `의`)가 붙은 꼴이고 뗀 뒤 두 글자 이상이 남을 때만이다(`영희이`·`치삼야`·`순이`는 변형이 아니다). `same_name` 링크의 근거 인용에는 두 이름의 기본형이 들어 있으면 된다. 카드 이름은 처음 나온 호칭이고 다른 호칭은 별칭이다. 모델은 동명이인(`distinct`)과 이름이 다른 같은 인물(별칭)만 알린다. 대가: 모델이 동명이인을 놓치면 합쳐지고 작가가 초안에서 고친다 |
| 2. 항목 단위 제외 | 근거·참조·종류 검증을 통과하지 못한 대상·진술·관계는 항목 단위로 제외하고 코드별 건수를 회차 추출 결과의 `skipped`에 남긴다. 정체 정리에서 검증을 통과하지 못했거나 모델이 다른 대상이라고 가른 쌍을 합치게 돼 버린 링크의 수는 정체 결과의 `skippedLinks`에 남긴다. 검증을 통과한 같은 쌍의 중복 제안이나 작가가 검토할 「동일 인물」 후보는 이 건수에 포함하지 않는다. 모델 호출 실패·시간 초과·잘린 응답·형식 오류와, 제안은 있었는데 검증된 대상이 하나도 없는 회차만 회차 실패이고(아무것도 제안하지 않은 회차는 빈 추출이며, 모든 회차가 비어 카드가 0장이면 정리 단계가 `NO_SETTINGS_FOUND`로 끝낸다), 회차가 하나라도 실패하면 작업은 `failed`다. 카드 본문·문서(대상별 칸)가 3,000자를 넘기게 되는 진술은 추출 때 그 진술만 제외하고(`DOCUMENT_TOO_LONG`), 이미 나온 대상의 뒤 회차 재서술은 카드 본문(IDENTITY)·GOAL에 싣지 않는다(인물의 SOUL은 정책 6, 인물이 겪거나 알게 된 것은 그 회차 기억에 들어간다. 이 제외는 건수에 잡히지 않는다). 회차 추출·정체 정리에서 제외한 건수와 적재 예약에서 제외한 관계 수를 공개 응답 `build.skippedItems`로 화면에 알린다. 원본 추출은 전부 `manuscript_build_result`에 남는다 |
| 3. 시작 전 기억 | 원문에 '이야기 시작 전부터' 같은 정해진 문구를 요구하지 않는다. `knownFromEpisode=0`(`kind=fact`, `occurredEpisode=0`, `document=memory`)은 인물의 첫 등장 회차이면 `episodes{"00"}`, 뒤 회차에서 밝혀진 것이면 그 회차 기억(`episodes{"NN"}`)에 싣는다. 소급하지 않아 미래 정보가 앞 회차로 새지 않는다. 사실 여부를 낱말로 가르는 금칙어 검사(계획·추측·것 같·소문 등)는 두지 않고, 종류 구분은 프롬프트와 표지가 맡는다 |
| 4. 대상 종류 | 대상 종류는 `character/location/organization/object/rule`이다(`rule`은 세계의 규칙·개념). `rule` 카드는 `rule` 유형·영역 `special`(특수 규칙)로 적재한다 |
| 5. 추출 중 변경 | 추출하는 동안 원고 저장 버전, 세계관 초안(기준 revision·관계 버전·확정 버전), 작품-세계관 연결이 고정한 입력과 달라지면 고정본으로 계속하지 않고 작업을 `failed`로 두고 사유 코드 `SOURCE_CHANGED`·`WORLD_CHANGED`·`WORLD_LINK_CHANGED`를 남긴다. 같은 작업을 재개해도 같은 거절이 반복되므로 화면은 실패한 작업에 항상 '같은 작업 재개'와 함께 동의 뒤 '새로 시작'(새 key, 지금 작품에 연결된 worldId가 우선이고 없으면 실패한 작업의 worldId)을 보인다 |
| 6. 인물 문서 채움 (#839, 2026-11-24 사용자 결정) | ① **SOUL은 뒤 회차의 soul 진술까지 쌓는다**: 앞 회차부터 차례로, 같은 줄은 한 번만, 문서 한도(3,000자) 안에서 줄 단위로 넣고 넘치는 줄부터 뺀다(줄을 자르지 않고 건수에 잡히지 않는다). 첫 회차에 이름만 스치고 뒤 회차에 성격이 드러나는 조연도 SOUL이 채워진다. IDENTITY(카드 본문)·GOAL은 이전처럼 첫 등장 회차의 진술만이다(정체·비밀이 앞 회차로 새지 않게). **한계(ponytail):** SOUL에는 회차 차원이 없어 시뮬레이션 기준 회차보다 뒤에 드러난 성격·말투가 섞일 수 있다. 회차별 SOUL은 `episodes`처럼 회차 키로 두는 별도 설계다. ② **이름으로 채우지 않는다**: 인물의 정체 진술이 없으면 카드 본문(`IDENTITY.md`)은 빈 문자열이다. 시뮬레이션의 `_filled`와 화면의 `missingCharacterDocs`가 '비어 있음'으로 알리고 작가가 세계관 관리 화면에서 직접 쓰거나 '원고로 채우기 제안'(연결된 소설의 저장 원고에서 찾은 문장을 작가가 승인해 초안에 반영, #847, [계약](world-review-contract.md#인물-문서-채우기-원고-근거-제안-847-사용자-결정-2026-11-25))을 받아 채운다. 확정 버전은 모든 카드에 본문이 필수라(Content `validate`, 화면 `worldSealIssues`) 채우기 전에는 확정할 수 없다. 인물이 아닌 카드는 같은 이유로 이름을 본문으로 둔다. ③ **대사에서 드러난 성격**: 추출 프롬프트가 서술자의 설명이 없어도 인물의 대사·행동에서 드러나는 말투·성격을 soul로, 그 대사 문장 하나를 인용해 적게 한다(인용 규칙은 그대로). ④ Content `ManuscriptStructureVerifier`도 같은 규칙이다(`nameKey`·`fit`, 정책 1·6). 적재(`load`)는 저장된 payload를 현재 규칙으로 다시 검증하므로, 배포 경계에서 이전 규칙으로 구조화 결과만 저장되고 적재 전이던 작업은 422로 거절되어 `CONTENT_REJECTED`로 끝나고 작가가 '새로 시작'한다(적재 요청을 이미 예약한 작업은 저장된 요청을 써서 영향이 없다) |

표기 계약(AI `organize`와 Content 검증기가 글자 그대로 같아야 한다): 카드 본문·문서 줄은 `<표지> <인용>`이고 표지는 사건 `[사건]`, 묘사 `[묘사]`, 사실 `[사실]`, 규칙 `[규칙]`, 계획 `[계획]`, 목표 `[목표]`, 추측 `[추측]`이다. 사건 카드 제목은 `{n}화 · {인용 앞 24 코드포인트}`(코드포인트 기준, UTF-16 단위로 자르지 않는다)이고 본문은 `발생: N화 / 참여: 이름들` 줄과 `[사건] <인용>` 줄이다. 관계는 label이 관계명이고 설명(body)이 근거 인용이다. 모델이 내는 관계 변화 값은 `started`·`ended`뿐이고 `fromEpisode`(현재 회차)와 `ended`는 프로그램이 채운다. Content 적재는 이미 이어진 관계의 재시작과 시작이 기록되지 않은 종료를 싣지 않는다(적재를 거절하지 않는다).

## 자동 적재 공개 정책 (2026-11-17 확인)

최초 일괄 세계관 구축만 대상으로 한다. 첫 등장 회차는 `semanticMetadata.preprocessing.firstEpisode`에 보존하며, 자동 생성 카드는 `visibility=private`로 저장하고 `semanticMetadata.revealFromEpisode`는 설정하지 않는다. 독자 공개 회차는 작가가 직접 지정한다. 기존 작가 데이터는 변경하지 않는다. 초안 적재·작가의 확정 버전 생성·독자 공개·작품 발행은 별도다. 이전 LoadPayload의 `revealFromEpisode=첫 등장` 의미를 그대로 공개 필드에 연결하지 않는다. 기존 원고 DTO의 `firstAppearanceEpisode`는 Content가 이전 입력을 읽을 때만 허용한다. 이전 카드의 저장값은 소급 변경하지 않는다.

통합 스키마는 develop V1~V12·V14 위에 원고 구축 V15를 적용한다(V13은 결번). 원고 구축 SQL이 V9로 기록된 기존 QA DB는 원본을 보존하며, 직접 업그레이드와 데이터 이관은 별도 검증 대상으로 둔다.

## 최초 구축 작업의 상태와 복구

작품 소유자의 접수와 조회에는 기존 V41의 작업 ID와 공개 상태를 사용한다. 운영 감시는 같은 행을 조회한다. WorldStudio V15의 세 테이블은 이 작업에 종속된다.

- `manuscript_build_job`은 동일 ID에 접수 당시 회차, 저장 버전, 해시, 작가와 세계관을 고정한다. 실행권으로 중복 실행을 막는다.
- `manuscript_build_result`는 작업별 회차 추출 근거와 정체 통합 결과를 보존한다. 재실행은 보존된 성공 결과를 재사용한다.
- `manuscript_build_load_step`은 단계별 생성 ID와 요청 payload를 예약하고 적용 receipt를 보존한다. 적재 결과가 불확실하면 감시 상태는 loading이며 소유자 상세에는 unknown을 표시한다. 모든 회차 결과와 단계별 receipt가 확인돼야 completed가 된다.

V15 스냅샷이 없는 구 V41 실패 기록의 동일 ID 재실행은 409 PREPROCESSING_SNAPSHOT_MISSING이다. 읽기나 재개는 새 접수를 발생시키지 않는다. 적재 전 실패라는 근거가 있는 경우에만 작가가 새로 접수할 수 있고 새 ID에 현재 원고를 고정한다. 기존 실패의 진행 이력은 보존한다. 부분 적재 또는 결과 미확인이면 새 접수도 409 PREPROCESSING_LOAD_REVIEW_REQUIRED로 차단한다. 신규 회차 자동 반영과 구 작업 데이터 이관은 별도 범위다.

V41 접수 커밋 직후 중단되어 V15 입력이 비어 있으면 소유자 GET은 기존 queued 기록과 manual_review를 반환한다. 동일 작업 retry와 새 접수는 409 PREPROCESSING_SNAPSHOT_MISSING으로 차단한다. 정상 입력 준비 중에도 일시적으로 같은 상태를 볼 수 있으므로 먼저 GET으로 다시 확인한다. 상태가 계속되면 작업 ID로 원래 입력과 적재 여부를 조사한다. 경과 시간이나 스냅샷 부재만으로 실패 전환·재접수를 허용하지 않는다.

최초 입력 준비가 거절되어 V15 입력이 만들어지지 않았다면(이미 설정이 있는 세계관 409 등) 방금 만든 V41 접수 행을 지운다. 접수가 성립하지 않았으므로 실패 행으로 남겨 작품이 적재 확인 대기로 막히게 하지 않는다. 입력이 만들어진 뒤의 실패만 `failed` 행으로 남긴다.
