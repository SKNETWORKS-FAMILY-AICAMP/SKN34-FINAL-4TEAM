# STORYFORK 시스템 아키텍처 설계 — RDB 기반 MVP

> **상태: 설계 초안 · 업무 기능 미구현.** MVP에서는 KAG·지식 그래프·Gitea를 쓰지 않고 세계관을 Core 소유 **PostgreSQL**에 저장하며, 스키마는 **Flyway**로 관리합니다(DEC-17). 세계관의 회차별 갱신은 **댓글이 달리는 게시판 방식**으로 기록하고(DEC-20), AI는 **도구로 Core 조회 API를 호출**해 필요한 설정을 읽습니다(DEC-21). pgvector·Langfuse·Core ↔ AI 내부 통신 인증·크레딧은 MVP 이후이며, MVP는 시연용 핵심 기능만 만듭니다(DEC-23).
>
> 기존 기능·정책은 [유스케이스](../usecase.md)와 [상세 명세](../usecase-spec/README.md)를 따르고, 이 문서는 정본 저장·AI 문맥 전달·MVP 범위를 정합니다. 이전 KAG 설계는 [보관본](archive/kag-design/design.md)으로 남깁니다.

## Overview

### 목표

작가는 세계관과 원고를 관리하고 직접 집필하거나 AI의 도움을 받습니다. 독자는 허용된 원작에서 Fork하여 독립적으로 창작하고 댓글·제보를 남깁니다. 저장 방식을 단순하게 바꾸더라도 **권한, Fork 고정, 정보 범위, 승인과 발행의 분리**는 유지합니다.

## MVP 범위

MVP는 **팀 시연용**이며(DEC-23) 기획서 핵심 기능을 실제로 보여 주는 데까지만 만듭니다. 외부 공개·운영은 범위 밖이고, 단계는 MVP 하나만 둡니다. 새로 들이는 기술은 PostgreSQL과 Flyway뿐입니다.

### 시연 흐름

1. 작가가 가입·로그인하고 세계관(인물·장소·관계)을 만든 뒤 작품을 연결합니다.
2. 회차를 쓰며 항목에 회차별 갱신 기록을 남기고, 독자 공개 회차와 인물별 인지 회차를 정합니다.
3. AI 다중 인물 시뮬레이션으로 전개 후보를 보고, AI 집필 제안을 받아 원고에 채택한 뒤 발행합니다.
4. 독자가 회차를 읽고 댓글·제보를 남기며, 작가가 제보 목록을 확인합니다.
5. 독자가 원작 회차에서 Fork해 분기 시점에 공개된 설정만 받은 독립 작품을 이어 씁니다.

### 포함과 제외

| 기획서 핵심 기능 | MVP 포함 | MVP 제외 |
|---|---|---|
| ① 작품·세계관(UC-02·07·24) | 내 세계관 1개를 작품 1개에 연결, 항목·관계 작성, 게시판 방식 갱신 기록, 작품 Fork 허용 설정 | 다른 작가 세계관 이용·세계관 Fork·조합(UC-05), 작품당 세계관 여러 개, 설정 자동 추출(UC-04), 원고 가져오기(UC-03) |
| ② 캐릭터·관계(UC-06) | 인물·관계 항목, 작품별 독자 공개 회차, 인물별 인지 회차 | — |
| ③ 다중 인물 시뮬레이션(UC-09) | 작가의 시뮬레이션 실행·결과 선택, AI 도구 조회 | 독자 스토리 오류 검증(UC-09 A5) |
| ④ Fork(UC-08) | 원작 회차 기준 Fork 생성, 분기 시점 복사, 원작별 1회·Fork의 Fork 금지 | 원작 삭제·탈퇴 후 처리 화면 |
| ⑤ 집필·발행(UC-10·11·13) | `.txt` 에디터 작성, 초안 저장, AI 집필 제안·채택, 발행·열람(UC-01은 작품 목록과 회차 뷰어만) | 저장 버전 이력·복원, 이미지·EPUB, 설정 검토(UC-12), 자율 연재(UC-18), 검색·좋아요·관심·이어 읽기 |
| ⑥ 독자 피드백(UC-14) | 댓글·제보 등록, 작가의 제보 목록 | 유해 콘텐츠 1차 필터, AI 분석·응대(UC-15), 수정안(UC-16) |
| 계정(UC-22) | 이메일·비밀번호 가입·로그인, JWT 접근 토큰 | 갱신 토큰·기기 관리, 이메일 인증·비밀번호 재설정, 탈퇴 |
| 비용(UC-17) | Core의 AI 작업 기록(모델·토큰·상태). 비용 상한은 OpenAI 프로젝트 예산 한도로 막음 | 크레딧, 앱 안의 요청 횟수 제한 |
| 운영(UC-20·21·23·26~28) | 오류 로그 | 전부 제외. 시연용 원작은 일반 작가 계정으로 직접 만듦 |

기존 MVP 제외(유료 공개, UC-19, UC-25, 일러스트, Elasticsearch, 구독·결제)도 그대로입니다. 제외한 기능의 정책은 [유스케이스](../usecase.md)와 명세에 남아 있으며 시연 이후 다시 정합니다.

### 시연용 단순화의 한계

- **접근 토큰만 사용:** 갱신 토큰이 없어 토큰이 만료되면 다시 로그인합니다. 외부 공개 전에 UC-22의 갱신 토큰 정책을 구현해야 합니다.
- **1차 필터 없음:** 댓글·제보를 검사 없이 공개합니다. 시연 참가자가 팀원이라는 전제이며, 외부 공개 전에 UC-14의 필터를 넣어야 합니다.
- **앱 안의 비용 제한 없음:** OpenAI 프로젝트 예산 한도에 의존합니다. 한도 도달 시 AI 작업은 실패로 표시합니다.

## Architecture

### 구성과 호출 방향

```text
브라우저 → web → 공개 Core API → 내부 AI Service → OpenAI
                         │  ↑
                         │  └─ AI 도구의 조회 호출 (작업 범위로 제한된 내부 조회 API)
                         └─ core-postgres (Flyway)
```

- **Core:** 사용자를 인증하고 대상별 권한·공개·권리 제한을 판단하며 정본을 저장합니다. AI 작업을 만들 때 작품·기준 회차·대상 인물 등 **조회 범위를 고정**하고, AI의 조회 요청에 그 범위 안의 내용만 돌려줍니다.
- **AI Service:** 작업 요청을 받아 제안을 생성합니다. 필요한 설정은 도구로 Core 조회 API를 호출해 읽고, DB에 직접 접근하거나 정본을 고치지 않습니다.
- **web:** 공개 Core API만 호출합니다. 화면에서 버튼을 숨기는 것은 서버 권한 검사를 대신하지 않습니다.
- 기본 방향은 `web → Core → AI Service → OpenAI`입니다. AI → Core 조회 호출은 읽기 전용 예외이며 쓰기·권한·발행·과금 판단은 하지 않습니다(DEC-21).
- Core ↔ AI 내부 통신 인증은 **MVP 이후**입니다(DEC-19). MVP에서는 AI Service와 Core 내부 조회 API를 호스트에 공개하지 않습니다. 이것은 인증을 대신하지 않으므로 로컬 검증 범위를 넘어 배포하기 전에 정합니다.
- Langfuse 추적은 **MVP 이후**입니다(DEC-18). MVP 동안 AI 사용량·상태·실패는 Core의 AI 작업 기록으로 확인합니다.

## Data Models

### 데이터 소유

| 데이터 | 저장 | 지켜야 할 점 |
|---|---|---|
| 세계관 항목·관계와 갱신 기록 | PostgreSQL. 게시판 방식(아래) | 기록은 추가만 하고 고치거나 지우지 않음 |
| 작품·회차·초안·발행본 | PostgreSQL | 초안과 독자 발행본 구분 |
| 작품별 회차 기록(설정 유효·독자 공개·인물별 인지 회차, `@` 연결) | PostgreSQL | 세계관 기록과 분리. 같은 항목도 작품마다 공개 회차가 다름(BR-10) |
| Fork | PostgreSQL. 분기 시점의 허용 내용을 Fork 전용 세계관으로 복사 | 원작 후속 변경이 들어오지 않음 |
| AI 작업·제안, 댓글·제보 | PostgreSQL | 제안·사용자 결정·실제 반영·발행 구분 |

### 세계관: 게시판 방식 (`확정`, DEC-20)

| 게시판 | STORYFORK |
|---|---|
| 게시글 | 세계관 항목(인물·장소·세력·규칙·사건)과 인물 관계 |
| 댓글 | 항목의 **갱신 기록**. 내용, 반영 회차, 작성자·작성 방식(직접 편집 등) |
| 댓글 목록 | 항목의 변경 이력 |

- **이력:** 갱신 기록은 추가만 합니다. 정정·되돌리기도 새 기록으로 남기므로 덮어쓰기·병합이 없습니다(BR-10).
- **현재 상태:** 항목마다 마지막 갱신 기록이 현재 내용입니다.
- **고정 시점:** 이용 허가 철회처럼 특정 시점에 고정해야 하면 그때의 마지막 기록 ID를 연결에 저장하고 그 ID까지의 기록만 읽습니다.
- **동시 편집:** 편집 화면은 읽은 마지막 기록 ID를 함께 보냅니다. 저장 직전에 마지막 기록이 바뀌었으면 덮어쓰지 않고 충돌을 알립니다(CE-07).
- **공개·인지:** 독자 공개 회차와 인물별 인지 회차는 세계관이 아니라 작품별 회차 기록에 항목 단위로 둡니다. 한 항목 본문에 공개 시점이 다른 사실이 섞이면 작가가 항목을 나눕니다(`제안`).

**개념 테이블 (`제안`):** `world_item`(항목), `world_item_update`(갱신 기록), `work_item_record`(작품별 회차 기록), `work_knowledge`(인물별 인지). 실제 컬럼·인덱스는 첫 구현 때 Flyway로 정합니다.

### Fork 고정 (`제안`)

1. Core가 원작·선택 회차·Fork 허용·권리 제한을 확인합니다. 원작 세계관의 공개 여부는 따지지 않습니다(UC-08).
2. 기준 회차까지의 발행 원고 버전을 고정합니다.
3. 원작에서 기준 회차까지 독자에게 공개된 항목만 골라 **분기 시점의 마지막 갱신 내용**을 Fork 전용 세계관의 첫 기록으로 복사하고, 작품별 회차 기록도 복사합니다(`INSERT…SELECT`). 비공개 항목과 이후 기록은 복사하지 않으므로 Fork에서 원작 비공개 내용을 조회할 경로가 없습니다.
4. 1~3을 한 DB 트랜잭션으로 처리하고 실패하면 부분 Fork를 남기지 않습니다. 원작별 독자 1회 제한은 유일 제약으로 막습니다.
5. 원작이 나중에 바뀌거나 삭제돼도 Fork는 복사본을 쓰므로 영향을 받지 않습니다. 삭제된 원작의 분기 전 원고 숨김 등은 UC-08을 따릅니다.

회차별 설정 이력이 없는 일괄 등록 원작은 현재 공개 상태로 고정하고 경고·동의를 받습니다(BR-14).

## Components and Interfaces

### AI 도구 조회 (`확정`, DEC-21)

```text
요청 → Core: 인증·권한 확인, AI 작업 생성(작품·기준 회차·목적·대상 인물 고정)
     → Core → AI Service: 작업 ID와 요청 입력
     → AI Service 도구 → Core 내부 조회 API (작업 ID 기준, 읽기 전용)
     → Core: 작업 범위·공개 회차·인물 인지로 걸러 응답
     → AI Service: 제안·근거 항목 ID·사용량 반환
     → Core: 형식·근거 확인 후 제안으로 저장 → 사용자 승인 후 반영·발행
```

| 도구(가칭) | 모델이 주는 값 | Core가 정하는 범위 |
|---|---|---|
| `search_items` | 검색어(이름·별칭) | 작업의 작품·기준 회차, 독자 또는 인물 범위 |
| `get_item` | 항목 ID | 범위 밖이면 "없음"과 같은 응답 |
| `get_relations` | 항목 ID | 범위 안의 직접 관계(1단계)만 |

- **범위 고정:** 모델은 검색어와 항목 ID만 정합니다. 작품·회차·인물 범위는 작업 생성 때 Core가 고정하며 요청마다 다시 받지 않습니다.
- **목적별 범위:** 작가 집필은 그 작품의 권한 범위, 독자 대상 작업은 독자가 본 회차까지의 공개 범위, 시뮬레이션 인물 역할은 그 인물이 그 시점에 아는 사실만 돌려줍니다. 다른 작가 세계관의 비노출 항목은 돌려주지 않습니다.
- **단순 작업:** 필요한 정보가 정해진 작업은 Core가 `@` 연결 항목을 미리 모아 보내도 됩니다. 도구 조회는 필요한 정보가 그때그때 달라지는 시뮬레이션 등에 씁니다.
- **근거 확인:** Core는 AI가 반환한 근거 항목 ID가 그 작업 범위 안인지 확인합니다. 이것은 출처 검사일 뿐 답변의 사실성이나 숨은 누설이 없음을 보장하지 않습니다.
- AI 결과는 제안입니다. 생성 성공과 저장·발행 성공은 다르며, 근거 부족·AI 오류·잘못된 출력은 성공으로 숨기지 않습니다.

### 검색의 한계

이름·별칭 검색과 1단계 관계 조회는 동의어, 대명사, 여러 단계 관계를 놓칠 수 있습니다. MVP에서는 pgvector와 임베딩을 쓰지 않고(DEC-17), 부족한 사례가 확인되면 MVP 이후에 검토합니다.

## Error Handling

- 저장 실패·갱신 충돌 시 이전 정본과 발행 상태를 유지하고 실패 또는 재확인을 알립니다.
- Fork 생성이 실패하면 성공으로 표시하지 않고 부분 데이터가 남지 않게 합니다.
- AI·네트워크 오류, 시간 초과, 근거 부족을 구분해 실제 상태로 표시합니다.
- 권한 밖 정보의 본문·존재 여부, 내부 오류와 비밀값을 공개 응답이나 로그에 노출하지 않습니다.

## Security Considerations

- Core가 모든 조회·변경에서 대상 권한과 공개 범위를 적용합니다. 클라이언트나 모델이 보낸 ID·범위를 신뢰하지 않습니다.
- 원고·사용자 입력은 지시가 아닌 데이터로 취급하며 AI에 DB 접근·쓰기 권한을 주지 않습니다.
- AI 작업 ID는 추측하기 어려운 값으로 만들고, 완료·실패·취소된 작업의 조회 요청은 거절합니다(`제안`).
- OpenAI 키는 AI 런타임에만, DB 접속 정보는 Core 런타임에만 둡니다. 브라우저 번들·이미지 빌드에는 넣지 않습니다.
- 현재 Compose는 인증·TLS 없는 로컬 검증용이며 인터넷 운영 배포가 아닙니다.

## Testing Strategy

다음은 **향후 구현 시의 검증 계획**이며 이 문서 작성으로 실행한 테스트가 아닙니다.

1. **갱신 기록:** 추가만 되는지, 고정 기록 ID 기준 조회, 동시 편집 충돌 시 기존 기록 보존.
2. **Fork:** 분기 후 원작 수정·공개 전환·삭제가 Fork에 영향을 주지 않는지, 비공개 항목이 복사되지 않는지, 실패 시 부분 생성이 없는지, 원작별 1회 제한.
3. **AI 도구 조회:** 작가·독자·인물별 범위가 다르게 걸리는지, 미래 회차·비노출 항목·범위 밖 ID 요청이 "없음"으로 응답되는지, 종료된 작업의 조회 거절.
4. **작업 상태:** AI 오류·시간 초과·근거 부족·취소가 제안·반영·발행 상태와 섞이지 않는지.
5. **보안·복구:** 로그 마스킹, Flyway 마이그레이션 적용, DB 백업·복구. 실제 유료 모델 호출은 별도 승인을 따릅니다.
