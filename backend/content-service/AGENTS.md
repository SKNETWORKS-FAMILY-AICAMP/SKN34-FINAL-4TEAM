# 콘텐츠 서비스 구현 지침

`backend/content-service/**`에 적용한다. [루트 공통 지침](../../AGENTS.md)과 [콘텐츠 이관·서비스 연동 계약](../../docs/design/content-service-migration-contract.md)을 함께 따른다.

- 작품·에피소드·원고·버전·세계관·WorldStudio·Fork·발행·콘텐츠 첨부와 콘텐츠 인가를 담당한다. 다른 서비스의 Entity·Repository·DB를 직접 쓰지 않는다.
- Kotlin 패키지는 `ai.storyfork.content`다. 기능별 Controller → Service → Repository 구조와 JPA를 사용한다.
  공개 DTO는 `service/dto`, 외부 계약은 `client/dto`에 두고 Entity를 HTTP로 노출하지 않는다.
  그 밖의 레이어·DTO·이름 규칙은 [Core 지침](../core-api/AGENTS.md)을 이 앱의 패키지에 맞춰 적용한다.
- 인증은 `CoreAuthClient`(Spring HTTP Service proxy)로 Core `POST /internal/v1/auth/verify`를 호출한다.
  사용자 Bearer와 `X-Content-Service-Token`을 함께 보내고 검증된 회원 UUID를 Principal로 쓰고 Core가 알려 준 운영자 여부(`operator`)는 `ROLE_OPERATOR` authority로만 쓴다. JWT 서명 키·Core Entity를 가져오지 않는다.
- 회원이 시작하는 AI 호출 클라이언트(제안·새 원고·부분 수정, 장르·키워드 추천, 초기 세계관·설정집 검토)는 `buildRestClient(..., forwardUser = true)`로 만들어 처리 중 요청의 Bearer를 `X-User-Authorization`으로 전달한다(`UserBearerInterceptor`, DEC-55 추적의 회원). 백그라운드와 같이 쓰는 색인 임베딩 클라이언트에는 달지 않는다. 집필 AI 오케스트레이션 `target`에는 Fork 작품일 때만 `fork: true`를 싣는다.
- 작성자·작가 표시명은 저장하지 않는다. 응답마다 `CoreNicknameService`(같은 `CoreAuthClient`, 서비스 토큰만)로 회원 ID 묶음을 한 번 조회해 채우며, Core에 없으면 `탈퇴한 회원`, 호출 실패는 503/504/502로 응답하고 대체 이름을 쓰지 않는다. Content↔Core 테이블 JOIN은 없다.
- 기존 API·CSRF·UUID·revision·잠금·불변 이력을 유지한다.
- Flyway: 콘텐츠 스키마는 `ContentPersistenceConfig.MIGRATION_LOCATIONS`의 `db/migration/{work,episode,world,episode_version,publication,fork,proposal,plan,preprocessing,sample}`와
  단일 `content_schema_history`다. 버전은 경로를 가로질러 전역으로 매기며(현재 V1~V31·V36~V45, V24는 결번이며 V32~V35는 열린 PR 몫) 새 SQL은 최댓값 다음 번호를 쓰고 결번은 채우지 않는다(`outOfOrder` 미사용).
  `sample/V16`은 CSV에서 생성한 개발 샘플 행이며 직접 편집하지 않는다. 샘플 변경은 다음 번호의 새 마이그레이션으로 한다.
  `db/migration/content`·root 직하 SQL을 다시 만들지 않는다. Auth·첨부·WorldStudio SQL 이력은 보존하고 자동 repair/reset하지 않는다.
- WorldStudio는 `contentDataSource`를 재사용하고 시작 시 전용 schema(`world_studio_schema_history`)를 migrate한 뒤 전용 EntityManager/TransactionManager로 validate한다. 별도 DB·분산 transaction을 추가하지 않는다.
- 세계관 삭제는 소프트 삭제(WorldStudio V9 `world.deleted_at`)다. `StudioWorldRepository`의 `lockOwned`·내 목록·`listed`·`listedByGenre` 쿼리와 `PublicWorldService.listedWorld`·`readerSnapshot`, `WorldCoverService.read`·`WorldCardImageService.read`, `WorkWorldService.link`의 `findById` 확인이 `deletedAt`을 거르므로 새 조회·쿼리도 같은 조건을 둔다. 연결된 소설(`work.world_studio_id`)이 있으면 409 `WORLD_LINKED`이며 컨트롤러가 연결을 먼저 읽어 `WorldStudioService.delete`에 넘긴다(두 트랜잭션을 겹치지 않는다). 확정 버전 되돌리기(`WorldStudioService.restore`)는 초안의 카드만 되돌리고 관계·새 확정 버전은 건드리지 않으며, 사라질 카드가 현재 관계의 끝점이면 409 `WORLD_RESTORE_BLOCKED`다. [계약](../../docs/design/worldstudio-independent-schema.md#확정-버전으로-카드-되돌리기와-세계관-삭제-2026-11-17)
- 설정집 AI 검토(`POST /world-studios/{id}/reviews`)는 성공한 결과를 WorldStudio `world_review_result`(V12, 세계관당 1행 upsert, AI 호출은 트랜잭션 밖)에 저장하고 `GET …/reviews/latest`로 소유자에게 돌려준다(#555, [계약](../../docs/design/world-review-contract.md#검토-결과-저장-2026-11-19-사용자-결정)).
- 장르(DEC-56)의 정본은 Content `genre` 표다(V42 `active`·`position`·`featured`·`emoji`, `name` UNIQUE, 코드 `genre-NN`은 서버가 다음 번호로 만들고 삭제는 없다). `GenreService`가 목록·추가·수정·순서를 맡으며 쓰기는 모든 장르 행을 잠근 트랜잭션 하나에서 검사·저장하고 응답은 커밋 뒤에 만든다(사용 수의 WorldStudio 읽기와 트랜잭션을 겹치지 않는다). 공개 `GET /api/v1/public/genres`(비로그인)는 활성만, 운영 내부 `/internal/v1/genres`(운영 서비스 토큰 체인)는 숨김 포함과 사용 수(집계 쿼리 한 번씩)를 준다. 홈 칩(활성이면서 `featured`)은 최대 6개다(409 `GENRE_FEATURED_LIMIT`). 작품 등록·수정(`WorkService`)·장르 추천 AI(`WorkTagSuggestionService`)·세계관 공개 설정(`WorldStudioService.publication`)은 활성 장르만 새로 고르고, 저장된 값은 숨겼어도 그대로 두면 통과한다. 세계관 장르는 WorldStudio V14(V13은 결번)가 CHECK를 지우고 옛 영문 코드를 Content 코드로 바꾼 값이며 FK 없이 서비스가 확인한다. 템플릿 시더의 장르 매핑은 같은 변환표이고 시스템이 정하는 값이라 활성 여부는 보지 않는다(원본 판정이 저장된 장르와 이 값을 비교한다). [계약](../../docs/design/genre-management-contract.md)
- 장르 템플릿 세계관은 SQL 마이그레이션이 아니라 `GenreTemplateSeeder`가 서버 시작 시 `WorldStudioService`(create → edit → save)로
  Core `auth/V8` 운영 관리자(`GenreTemplateSeeder.TEMPLATE_OWNER`, 임시 할당) 소유 WorldStudio 세계관으로 적재한다. 리소스는 `genre-templates.json`이며
  소유자 한계(공개 비밀번호·소유자 불일치·타 사용자 미노출)를 포함한 [설계](../../docs/design/worldstudio-independent-schema.md#플랫폼-장르-템플릿-세계관)를 따른다.
  새 템플릿은 세계관과 카드를 공개(`visibility=public`)로 생성한다. 기존 템플릿은 고정 입력·이력·관계가 모두 원본인 경우 한 번만 공개하고 세계관별 marker로 이후 비공개 선택을 보존한다(DEC-45·46).
- 확장 역사·전승 후보는 별도 `ExpandedTemplateSeeder`의 기본 켠 `app.worldstudio.expanded-seed-enabled`로 시연에 적재한다(사용자 결정 2026-11-18). 관계는 DEC-54 읽기 규칙으로 정규화한다(#531). 원전 권리·독립 감수는 #425에서 계속한다. 플래그가 꺼져도 이미 시작한 미완료 marker는 같은 입력·hash로만 재개한다. 없는 세계관은 비공개 생성해 카드·관계 청크를 전부 기록하고 마지막 확정과 공개를 같은 PG 트랜잭션에서 처리한다. 기존 26종과 저장 완료된 역사 7종은 원본 검사를 통과할 때만 확장하며 옛 카드와 공개 선택을 보존한다. 미완료 중 공개 관계는 unavailable이고 사용자 쓰기·AI 검토는 충돌로 보류한다. 과거 미완료 역사 요청은 보류한다.
- 설정 카드의 공개 설정은 하나('N화부터 공개' 또는 '작가 전용', 기본 작가 전용)다(DEC-53). 독자 설정 위키(`GET /api/v1/public/works/{id}/world-cards`)·공개 세계관(상세·목록 수·이미지)·가져오기·Fork 이어받기·공개 MCP는 같은 규칙으로 서버가 거른다:
  유효 공개 회차(`semanticMetadata.revealFromEpisode`, 없고 `visibility=public`이면 1)가 기준 회차(연결된 소설의 발행된 마지막 회차, 소설이 연결되지 않았으면 1) 이하인 카드와 그 시점의 관계만 보낸다. 화면에서 거르게 두지 않는다. 키가 있는데 값이 잘못된(JSON `null` 포함) `revealFromEpisode`는 작가 전용으로 닫는다(`visibility`로 열지 않는다). 모든 비작가 출구가 `shownCardEpisode` 한 함수를 쓰며(DEC-46의 '공개 세계관=`visibility`, 독자 설정 위키=`revealFromEpisode`' 두 기준을 대체), 공개 목록의 세계관별 기준 회차는 페이지 전체에 연결 작품 조회 한 번과 공개 작품의 마지막 발행 회차 쿼리(`WorkRepository.lastPublishedOfPublicWorks`) 한 번으로 센다. 카드·관계 본문의 링크 `[글자](card:<uuid>)`는 응답에 실리는 보이는 카드에 없는 대상이면 `PublicWorldService`가 `hideCardLinks`(`world/domain/CardLinks.kt`) 한 함수로 글자만 남기고 링크가 아닌 모양(`<card:id>`·제목이 붙은 링크 등)에 남은 `card:<uuid>`도 같은 기준으로 지운다(상세·독자 위키·Fork 이어받기 응답, REST·MCP 공통). AI로 가는 요청(세계관 검토 `WorldReviewInput`·초기 분석 입력 `InitialWorldInput`의 카드 본문 출처·원고 Q&A의 관계 근거)에는 `stripCardLinks`로 모두 글자로 벗겨 id가 모델에 섞이지 않게 한다(초기 분석은 출처 해시·근거 구간이 벗긴 글 기준이고 `validateAgainst`가 같은 규칙으로 다시 만든다)([링크 규칙](../../docs/design/worldstudio-independent-schema.md#카드-본문-링크--dec-53)). [계약](../../docs/design/public-world-contract.md#카드-공개-기준-일원화--dec-53)
- 세계관과 소설은 1:1이다. 연결의 정본은 `work.world_studio_id`(UNIQUE) 하나이고 `WorkWorldService`가 맡는다. Content와 WorldStudio 트랜잭션은 겹치지 않게 차례로 연다. 공개 세계관 상세(`PublicWorldService.detail`)는 연결된 소설이 공개 작품(`WorkAccessResult.publiclyVisible()`)일 때만 그 최소 정보(`linkedWork`)를 싣고 그 밖은 `null`로 존재를 숨기며, 소설 작가명은 세계관 작가와 같은 `CoreNicknameService` 조회 한 번에 묶는다(목록은 바꾸지 않는다, #329).
- 자기 세계관을 연결하지 않은 `following` Fork는 원작 세계관을 읽기 전용으로 이어받는다(#365). `WorkWorldService.inheritedWorld` 한 곳이 조건·상한 회차(Fork 기준 회차)를 정하고 `PublicWorldService.inheritedWorld`가 확정 버전의 카드 중 유효 공개 회차가 상한 이하인 것(DEC-53: 독자 설정 위키와 같은 카드 집합이며 DEC-46·#365의 '공개 카드만'을 대체)과 그 카드끼리의 그 시점 관계만 거른다. 인물 문서·관계 본문 같은 작가용 값은 싣지 않는다. REST `GET /api/v1/works/{id}/inherited-world`·MCP `work_inherited_world`·`QaScopeService`가 같은 결과를 쓰며 원작 작가 권한으로 초안을 읽지 않는다. [계약](../../docs/design/public-world-contract.md#fork가-이어받는-원작-세계관-dec-3237-365)
- Fork 세계관 독립(#583): `POST /api/v1/works/{id}/inherited-world/detach`는 `WorkWorldService.detachInheritedWorld`가 이어받기와 같은 판정·같은 카드·관계 집합(`PublicWorldService.inheritedSource`)을 새 id로 복사(`world/domain/ForkWorldCopy.kt`)해 `WorldStudioService.create → edit`(확정 버전은 만들지 않는다)로 Fork 작가 소유 새 세계관을 만들고, Content 트랜잭션에서 작품 행과 `fork_world_reference` 행을 잠가 재확인한 뒤 연결·`independent`로 바꾼다. 생성 뒤 실패는 소프트 삭제하고, WorldStudio 쓰기를 Content 트랜잭션 안에서 열지 않는다. [계약](../../docs/design/public-world-contract.md#fork-세계관-독립--dec-37)
- `GET /internal/v1/works/{id}/leak-references`(`ForkLeakReferenceService`, 운영 서비스 토큰 체인 전용, DEC-55)는 위 공개 규칙의 여집합을 내보내는 **유일한 출구**다. 운영의 정보 누설 표본 검사가 글자 대조할 제목만 주며(본문 없음), Fork 기준 회차(Fork를 만들 때 고정한 원작 회차)에 독자에게 안 보이는 원작 카드(`PublicWorldService.hiddenCardTitles` = `shownCardEpisode`의 여집합이라 규칙을 따로 두지 않는다)와 그 기준 회차 뒤 원작 회차의 현재 초안·발행 버전 제목이다. 독자가 이미 읽을 수 있는 Fork 본문(물려받은 원작 발행본·Fork가 직접 발행한 현재 발행본)에 그대로 나오는 제목은 뺀다(공백만 정규화한 부분 문자열). 공개 응답·MCP·AI 요청에는 쓰지 않고 공개 proxy에 등록하지 않는다. Fork가 아니면 `originWorkId: null`과 빈 목록이다.
- 관계는 회차별 연결이다(DEC-51). 저장 요청의 `relationshipEpisodes`(관계 id → 그 관계의 'N화부터', DEC-54 2단계)가 있으면 `WorldStudioService.edit`이 `Neo4jRelationshipRepository.replaceWithEpisodes`·`readAfterWithEpisodes`를, 없으면 이전 경로(`replace`·`readAfter`)를 부르고(필드가 비면 직렬화하지 않아 요청 hash가 이전과 같다), 회차를 준 관계는 값이 같아도 새로 쓰는 관계라 양 끝이 활성 카드여야 한다(값은 정수 JSON 값만 읽는 `WholeEpisode`라 소수·문자열은 422). 공개 응답(`PublicWorldService.detail`·`readerCards`)만 관계마다 `history`를 싣는다: 이력은 저장소 `read(worldId, 기준 회차)`가 기준 회차 이하에서 그 시점 연결과 끝점이 같은 연속한 연결로 만들고(다른 카드로 옮겨지기 전의 옛 연결은 지금 보이지 않는 카드와의 관계일 수 있어 뺀다) `RelationshipStateResult.history`를 처음 읽을 때 계산해 `currentRelationships(withHistory)`인 상세·독자 위키만 풀고(소유자 읽기·저장·목록·Fork 이어받기는 풀지 않는다) 공개 경로는 늘 기준 회차로 읽고(최신으로 읽어 뒤 회차의 변화를 내보내지 않는다) 이력 `body`의 본문 링크도 관계 `body`와 같은 `hideCardLinks`로 치환한다(Fork 이어받기 응답에는 이력이 없다). - MCP 창구(`ai.storyfork.content.mcp`, `/mcp`)는 기존 Service 함수만 호출하는 어댑터다. 공개 도구는 인증 없이, 사용자 도구는 전달된 Bearer를 기존 필터로 검증한 회원 UUID로 호출하며 도구 인자로 회원 ID를 받지 않는다. [계약](../../docs/design/content-mcp-contract.md)

없으면 AI·검색·크레딧 예약 없이 `SerialReason.NO_WORLD`(`연결된 세계관이 없어 시뮬레이션으로 집필할 수 없습니다.`)로 끝내고(예약 앞이라 해제할 것이 없다), 읽기 실패는 `AI 생성에 실패했습니다.`로 끝낸다(연결 세계관을 읽지 못했다고 이어받는 세계관으로 대신하지 않는다). `ManuscriptQaService`가 internal이라 `SerialRunner`의 생성자도 internal이다. 원고 색인은 어느 환경에서나 항상 켜져 있다(`MANUSCRIPT_INDEX_ENABLED` 없음): `ManuscriptIndexConfig`에 조건이 없어 모든 Spring 컨텍스트가 시작할 때 Elasticsearch에 접속하므로 CI 통합 job이 Content에 Elasticsearch service를 띄우고, 새 환경(prod 포함)에는 `MANUSCRIPT_INDEX_URL`이 필요하다. 시뮬레이션 제안 글은 처음 확인한 게시판에만 저장한다(`SerialService.add`의 `boardId`, 바뀌었으면 409 `SERIAL_NO_BOARD`). 제안 글은 회원당 개수 제한이 없어 같은 회원의 동시 시뮬레이션도 서로 막지 않는다(예약 키가 따로다). 실패는 게시판을 고정 사유(`SerialReason`, AI 402 `CREDIT_LIMIT_EXCEEDED`는 `LIMIT` `크레딧 상한을 넘었습니다.`, 관련 장면 검색 실패는 `SEARCH`, 세계관 없음은 `NO_WORLD`)로 `failed` 처리하되 인물 시뮬레이션이 막은 실패만은 AI가 설명한 문구가 사유다(`SerialAiFailure.detail`: `SerialAiClient.failureDetail`이 AI 상태 409·422, `detail`이 문자열, `code`가 `SERIAL_REVIEW_FAILED`·`CREDIT_LIMIT_EXCEEDED`가 아님을 가려내고 `SerialRules.cleanReason`이 공백·줄바꿈·제어 문자를 한 칸으로 줄여 `REASON_MAX` 300자까지만 남긴다. FastAPI 검증 오류(`detail` 배열)·읽을 수 없는 본문·502·504는 해당하지 않아 `SerialReason.AI`(`AI 생성에 실패했습니다.`)로 남고, 502 장면 미완료 문구에는 모델이 쓴 이유가 섞여 이번 범위에서 뺐다. 응답 본문 전체는 로그에 남기지 않는다. `SerialAiFailure`의 메시지에도 싣지 않는다). 같은 대상 회차의 새 게시판에 선택지·투표(표의 기본키에 게시판이 있어 다시 만든다)·제안 글(추천은 글을 따라간다)·선택지 시도 시각을 옮겨 소유자가 다시 시도할 수 있게 한다. 켜기·설정 저장에는 세계관 연결이 필요 없지만(연결돼 있으면 카드가 문맥에 든다) 회차 실행에는 세계관(연결 또는 Fork가 이어받는 원작)이 필요하다. 설정 카드 제안은 만들지 않는다. 독자 게시판 읽기 `GET /api/v1/works/{id}/serial-board`만 `ContentSecurityConfig`에서 익명을 허용한다. 크레딧 상한은 `SERIAL_SIMULATION_CREDIT_LIMIT`(5)·`SERIAL_CHOICE_CREDIT_LIMIT`(5)·`SERIAL_SUMMARY_CREDIT_LIMIT`(5, 회차 본문 하나의 요약이 약 3크레딧)·`SERIAL_EPISODE_CREDIT_LIMIT`(1000: 인물 시뮬레이션 장면까지 같은 예약으로 센 추정 상한 — 시뮬레이션 없이는 3,900자 회차 실측 약 60, 문맥이 클 때 서비스 호출 최악 약 250, 장면은 보통 300~500이고 실측 전이라 첫 실행 뒤 다시 맞춘다. 소유자의 사용 가능 잔액이 이 값 이상이어야 예약된다)다. V43은 develop에 없어 투표·제안 개편과 회차 요약 표(2026-11-22)를 같은 파일에서 직접 고쳤다(이미 옛 V43을 적용한 로컬·개발 DB는 체크섬이 달라 기동이 실패한다: V43이 만든 표 전부 — `ai_serial`·`serial_board`·`serial_vote`·`serial_episode_summary`·옛 `serial_opinion` — 와 `content_schema_history`(Content 전용 Flyway 이력, `flyway_schema_history`는 Core Auth의 것이라 건드리지 않는다)의 V43 행을 지운 뒤 다시 올려야 하고 `ai_serial`의 설정 행도 사라지므로 개발 DB에서만 한다). 켜기·끄기는 운영 설정의 집필 방식 하나다: `WorkSettingsService`가 `writingMode`(`direct`·`assisted`·`autonomous`)를 저장할 때 같은 트랜잭션·작품 잠금 안에서 `work_automation_version` 새 행과 `SerialService.setEnabled`(`ai_serial.enabled`, 행이 없으면 기본값으로 생성)를 함께 바꾼다(V44가 `writing_mode` CHECK에 `autonomous`를 더한다). `autonomous`에서 다른 방식으로 바꿀 때 실행 중(`queued`·`running`)이면 409 `SERIAL_RUNNING`이고, `PUT …/ai-serial`은 요일·시각·방향만 바꾼다(요청의 `enabled`는 무시). `autonomous`(=`ai_serial.enabled`)인 동안 소유자는 1화만 직접 쓴다(2화부터는 409 `SERIAL_LOCKED`): 회차 단위 진입점(초안 저장·초안/회차 삭제·버전 저장·되돌리기·발행·공개 중단/재공개·예약 등록/수정·수정 제안 승인)이 소유 확인 뒤 자기 대상 회차 번호로 `WorkAccessService.requireEpisodeWritable`을 부르고(1화는 통과), 회차를 가리지 않는 쓰기(원고 가져오기, 이미 활성 회차가 있을 때의 새 회차 — 활성 회차가 없으면 1화 만들기라 통과)는 `requireManuscriptWritable`을, 작품 단위 저장·발행은 대상 회차(마지막 발행+1)로 `requireEpisodeWritable`을 부른다. 같은 서비스를 거치는 REST·MCP·집필 AI 반영이 함께 막힌다. 자율 연재 실행 자신의 저장만 `SerialService`가 `…ForSerial` 전용 진입점으로 건너뛰고(그 이름은 다른 곳에서 부르지 않는다, `SerialManuscriptLockTest`가 고정), 켜기 전에 등록한 예약 발행의 실행·예약 취소/목록·작품 정보·세계관·댓글은 막지 않는다. AI는 1화를 쓰지 않는다: 발행된 회차가 없으면 게시판을 열지 않고 지금 실행은 409 `SERIAL_NO_BOARD`이며 `runInput`도 대상이 2화 미만이면 거절한다.
